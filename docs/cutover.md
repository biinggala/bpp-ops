## 절차

### 1. 내보내기 (= 백업)

Firebase 콘솔 → Realtime Database → 데이터 탭 → **루트** 항목의 ⋮ → JSON 내보내기.
반드시 루트에서 받습니다. `cringe` 안쪽만 받으면 이메일과 계정을 잇는 `userProfiles`가 빠집니다.

받은 파일이 곧 롤백용 백업입니다. 안전한 곳에 따로 보관하세요.

### 2. 변환

```
node scripts/migrate.mjs <내보낸파일.json> \
  --out migrated.json \
  --drop-projects 0zh5xmxompiexzdf,j02e16symss8xsx0,29dn5mnemss9bt61,w6jowr2vmpigdusg
```

출력 마지막의 **`✓ 업무 건수 일치 — 유실 없음`을 반드시 확인**합니다.
어긋나면 스크립트가 0이 아닌 코드로 끝나며, 그때는 진행하지 않습니다.

보고서에 나오는 "주인을 찾지 못한 업무·마일스톤"은 위 결정에 따라 의도적으로 옮기지 않는
항목입니다. 목록이 예상과 다르면 멈추고 확인하세요.

### 3. 검증

```
firebase emulators:exec --only database --project demo-verify \
  --config firebase.test.json "node scripts/verify-migration.mjs migrated.json"
```

`✓ 모든 프로젝트가 멤버에게만 열립니다`가 나와야 합니다.

### 4. 점검창

팀에 공지하고 모두 앱을 닫게 합니다. 10분이면 충분합니다.
이 시간에 들어온 편집은 1번에서 받은 내보내기에 없으므로 유실됩니다.

### 5. 올리기

콘솔 → 데이터 탭 → **루트**의 ⋮ → JSON 가져오기 → `migrated.json`.
루트에서 가져오면 데이터베이스 전체가 교체됩니다. `migrated.json`에는 옛 `cringe` 노드가
그대로 들어 있어 되돌릴 여지가 남습니다.

### 6. 규칙과 앱 배포

```
git push origin main    # 규칙 교체는 이미 브랜치에 반영되어 있다
```

`deploy.yml`이 규칙과 앱을 함께 배포합니다. **순서가 중요합니다** — 데이터가 아직 옛 자리에
있는데 규칙만 먼저 바뀌면 앱이 즉시 멈춥니다.

MCP 서버(Cloud Run)도 같은 시점에 새 버전으로 올립니다.

### 7. 확인

- 로그인 → 사이드바에 내 프로젝트가 전부 보이는지
- 업무 목록·마일스톤이 예전과 같은지
- 다른 계정으로 로그인해 남의 프로젝트가 안 보이는지
- 업무 하나를 수정하고 다른 브라우저에서 반영되는지

## 되돌리기

되돌릴 방법이 두 겹입니다.

1. **호스팅과 규칙**: `main`을 이사 이전 커밋으로 되돌리고 push하면 옛 규칙과 옛 앱이 함께
   배포됩니다.
2. **데이터**: 1번에서 받아둔 내보내기 파일을 루트로 다시 가져옵니다.

`migrated.json` 안의 `cringe` 노드도 이사 시점의 사본이라 세 번째 수단이 됩니다.
